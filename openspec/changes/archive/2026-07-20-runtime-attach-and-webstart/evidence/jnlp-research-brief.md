# JNLP/WebStart research brief (Fable, 4 streams + synthesis)

# JNLP Support: Decision-Oriented Synthesis

## 1. The crux — this is an INJECTION + DISCOVERY problem, not an introspection problem

The evidence across all four streams converges hard on this. Defense:

- **The introspection engine already works.** Stream 4 is explicit: the wire protocol needs *zero* change. The Swing/SWT engines this library already ships drive JNLP-launched UI the same way they drive a directly-launched app, because `Window.getWindows()`/`Frame.getFrames()` are boot-loader APIs that a `JNLPClassLoader` cannot hide. The only in-agent hardening required is four already-solved-shaped problems: run discovery on the app EDT (AppContext scoping), resolve app/SWT classes via the JNLP loader (the *exact* Eclipse-RCP OSGi classloader fix this project already implemented in `EclipseWorkbenchHelper`), wrap SM-sensitive calls in `doPrivileged`, and gate readiness on a real "first app window exists" signal (the same "port-before-Display" timing bug already documented in MEMORY.md for RCP). None of these are new engine work — they are ports of fixes the project has already shipped for RCP.

- **The genuinely new, unsolved surface is getting the agent into the right JVM and finding that JVM.** Streams 1 and 2 establish the decisive structural fact: OWS and IcedTea-Web both launch the JNLP app in a **separate child JVM process** (OWS `OwsJvmLauncher` via `ProcessBuilder` → `com.sun.javaws.Main`; ITW `javaws` forks unless `-Xnofork`). So there is a distinct app PID — good for attach — but also a launcher JVM you must *not* attach to, and `-javaagent` is **not** on the JSR-56 secure vm-args whitelist and signing does not unlock it. That means the library's normal front door (put `-javaagent` in the launch) is closed by default for JNLP. This is the whole problem.

- **The library's existing capability is exactly the lever.** The agent already supports `agentmain`/dynamic attach, and JDK Attach + jps/jcmd are available. The `List Applications` keyword is currently a stub (`NotImplementedError`). So the work is: turn `List Applications` into a real JVM Discovery Service that identifies the OWS/ITW *app* child by command-line markers, then load the agent via attach. That is injection + discovery, full stop.

**Conclusion:** frame the proposal as "add a JVM discovery + attach-injection path, plus four small introspection-hardening ports," not "add JNLP introspection." Roughly 80% of the risk and novelty is in injection+discovery.

## 2. Recommended injection strategy split

**Single best default: dynamic attach (`agentmain`) after PID discovery.** It is the one vector that works in both worlds, requires no change to how the app launches, and reuses the library's existing `agentmain` support. Ship `jattach` (or a small JDK-attach helper) so it works even when the only Java present is OWS's bundled JRE.

| Context | Primary | Why | Fallback |
|---|---|---|---|
| **CI / controlled** | OWS `deployment.properties`: `ows.jvmargs.for.<jnlp>=-javaagent:...` + add `-javaagent` to `deployment.jvm.arguments.whitelist` | Targets *only* the app child JVM; no launcher double-load; fully reproducible; no attach-timing race | Dynamic attach |
| **Real-world end user** | Dynamic attach (`jattach`/`VirtualMachine.loadAgent`) after discovery | App is already running, you can't dictate launch; JRE-only friendly; warning-only on JDK 21+ | `deployment.properties` if you can pre-stage the user's OWS config |

**Explicitly reject `JAVA_TOOL_OPTIONS`/`_JAVA_OPTIONS` as anything but a last-resort scripted fallback.** It double-loads into the launcher JVM (IcedTea-Web #949: Java 8 launcher tried to load a Java 11 agent → `UnsupportedClassVersionError` before the app JVM even ran) and leaks into every Java process on the machine. If ever used, compile the agent to Java 8 bytecode and give `premain` a self-guard that no-ops unless it detects the app JVM.

Design principle: **dynamic attach is the default JNLP mode; `deployment.properties` injection is an opt-in documented for CI; env-var is discouraged.**

## 3. Recommended test harness + sample app strategy

Build determinism in-house; keep real apps as opt-in smoke tests only (mirrors the existing showcase-jar pattern in this repo).

- **Primary CI target — self-hosted minimal Swing JNLP (Rank #1).** A tiny `JFrame` main class → `app.jar`, a **sandbox** JNLP (omit `<security>` → no signing needed), served by `python3 -m http.server`, launched with OWS `javaws` under `xvfb-run -a`. This is the only fully deterministic option. Put it under `tests/apps/jnlp/` + a `tests/robot/jnlp/` suite that self-skips when OWS/`javaws` is absent (same convention as the showcase suites).
- **Signed / all-permissions variant** added only to exercise signed-jar + sandbox-permission paths: `keytool` + `jarsigner`, plus `Permissions: all-permissions` / `Codebase:` manifest entries.
- **Edge-case breadth:** lift individual fixtures out of IcedTea-Web `integration-tests/reproducers/{simple,signed,custom}` and self-host them the same way.
- **Second known-good app:** OWS's own `system-properties-printer` demo (a small Swing/JNLP app), if it builds standalone.
- **Runtime:** build a thin Docker image = JDK 11 + OpenWebStart + Xvfb (no official karakun image exists; borrow the `javaws`-under-container pattern from `vulturm/kvm-jnlp`, not the heavy LXDE approach).
- **Optional real-world smoke test (never a CI gate):** JClic `https://clic.xtec.cat/jnlp/jclic/reportServer.jnlp` (verified HTTP 200, all-permissions Swing). Self-skipping, opportunistic only — depends on XTEC's server.

The harness must **launch + attach in one process/command** and cannot assume the app persists across tool calls — and note the MEMORY.md sandbox gotcha: don't `pkill -f javaws`/`smart-client`-style patterns that match your own command line.

## 4. Top risks and mitigations

1. **JVM topology: in-process vs child (foundational).** Entire attach strategy assumes the app runs in a *separate* PID. If OWS is ever configured `-Xnofork`-equivalent / in-process, launcher and app collapse into one PID and the "attach to app not launcher" heuristic breaks. **Mitigate:** SPIKE — confirm child-JVM topology on the exact OWS/ITW versions targeted; document `-Xnofork` as unsupported/degraded.
2. **PID ambiguity (launcher vs app).** Must not attach to the bootstrap/launcher JVM. **Mitigate:** discovery filters on command-line markers — `openwebstart.jar` on `-Xbootclasspath/a`, `-Dnet.sourceforge.jnlp.runtime.Boot.basedir=`, main class `net.sourceforge.jnlp.runtime.Boot`, `ICEDTEA_WEB_SPLASH` env — plus a heuristic (app owns a visible AWT window). Note `jps` drops the package on short main-class form → prefer `jcmd`/`jps -v` full command line. **This must be empirically verified across OWS versions.**
3. **SecurityManager / sandbox (bifurcates on JDK version).** *Correction to the task premise:* an attach-loaded agent is **not** auto-granted `AllPermission` under an active SM — permissions come from its ProtectionDomain. **Mitigate:** (a) JDK 24+ (JEP 486) — SM permanently disabled, moot; (b) JDK 8/11/17 with SM — the `-javaagent` jar loads from the trusted system code source, but wrap `addAWTEventListener` (armPick), `new Robot`/`createScreenCapture`, `setAccessible`, and the RPC `ServerSocket` bind in `AccessController.doPrivileged` from an agent class to cut app frames off the check stack; or grant the agent codeBase `AllPermission`; or use a socket-free transport to dodge `SocketPermission`. Many enterprise JNLPs already request `all-permissions` (no effective sandbox).
4. **Attach warnings on JDK 21+ (JEP 451).** Attach still *works*, only prints a warning today; "disallowed by default" is a *future* release, not JDK 21/24. **Mitigate:** document `-XX:+EnableDynamicAgentLoading` as the forward-compatible opt-in for controlled launches; track the JEP.
5. **Launcher differences OWS vs IcedTea-Web.** Different `JNLPClassLoader` class names (`com.sun.jnlp.*` legacy Oracle 8 vs `net.sourceforge.jnlp.*` / `net.adoptopenjdk.icedteaweb.*`), different vm-arg filtering behavior across versions (e.g. OWS #322 dropped `--add-opens`). **Mitigate:** match a *set* of classloader names, not one string; verify the whitelist behavior against the specific OWS release targeted.
6. **Timing (port-before-UI, worse under WebStart).** `premain` socket is up before JNLP loader, app AppContext, and EDT exist; OWS startups run tens of seconds to minutes. **Mitigate:** gate `getUiTree` on a real readiness signal (WINDOW_OPENED `AWTEventListener` latch or poll `AppContext.getAppContexts()`); prefer `agentmain`/attach (UI already up) — which is the default anyway, so this risk is largely self-mitigating.
7. **AppContext scoping (silent empty tree).** `getWindows()` from the agent socket thread returns only the caller's AppContext → empty even with visible frames. **Mitigate:** run root discovery on the app EDT via `invokeAndWait`, or enumerate `AppContext.getAppContexts()`.
8. **Cross-process attach constraints.** Same-user/root required; PID-namespace/container boundaries block attach to `/tmp/.java_pidNNNN`. **Mitigate:** document; ensure automation and app share user + PID namespace.

## 5. Concrete experiments, priority order

1. **Topology + PID discrimination spike (highest value).** Install target OWS + ITW, launch the Rank-#1 sample JNLP, run `jps -lv`/`jcmd -l`, confirm (a) app runs in a distinct child PID and (b) the command-line markers reliably separate app from launcher across ≥2 OWS versions. *This validates the entire default strategy.*
2. **Attach round-trip.** `jattach <app-pid> load instrument false "/abs/agent.jar=port=..."` against the running sample; confirm the agent loads, binds its socket, and `getUiTree` returns the real Swing tree. Test with **only the OWS-bundled JRE on PATH** (no JDK) to prove `jattach` covers the JRE-only case.
3. **AppContext empty-tree reproduction.** Confirm `getWindows()` from the agent socket thread returns empty and that moving discovery to the app EDT fixes it — Stream 4 flags this as *not empirically verified*.
4. **`deployment.properties` CI vector.** Set `ows.jvmargs.for.<jnlp>=-javaagent:...` + `deployment.jvm.arguments.whitelist=-javaagent`; verify the agent loads into the app JVM only (no launcher double-load), and critically that the whitelist accepts the **colon-arg form** `-javaagent:agent.jar=args` (docs say whitelist stores name-only — needs source verification).
5. **Env-var double-load failure.** Reproduce IcedTea-Web #949 (set `JAVA_TOOL_OPTIONS`, watch launcher crash), then prove the Java-8-bytecode + `premain` self-guard mitigation survives it.
6. **SecurityManager matrix.** On a JDK 8/11 sandboxed (non-all-permissions) JNLP, confirm which agent operations (socket bind, `addAWTEventListener`, `Robot`) get denied and that `doPrivileged` wrapping fixes them. Confirm moot on JDK 24+.
7. **SWT-under-JNLP classloader.** Only if a real SWT JNLP app is in-scope: confirm `Class.forName("org.eclipse.swt.widgets.Display")` from the agent loader fails and that the `JNLPClassLoader`-resolution (EclipseWorkbenchHelper-style) fixes it.

## 6. Contradictions and low-confidence claims to verify

- **Task-premise correction (repeated by two streams, high confidence):** attach-loaded agents do **not** automatically run with `AllPermission` under an SM. Any proposal language assuming "the agent bypasses the sandbox for free" is wrong for pre-JDK-24 SM-active apps. Adopt the corrected view.
- **Whitelist mechanics (open, needs source verification):** does `deployment.jvm.arguments.whitelist` accept `-javaagent` including its `:jar=args` payload, or does name-only storage strip the value and make it unusable? And are `ows.jvmargs.for.{jnlp}` args also routed through `checkVMArgs()` (blocked unless whitelisted) or trusted as admin-supplied? This decides how friction-free the CI vector is — verify against the specific OWS release, don't trust the docs summary.
- **Toolkit split (medium confidence, no quantitative source).** "Swing dominates JNLP" is a reasoned inference, not measured. Fine for prioritization (Swing → SWT/RCP → JavaFX) but don't state a percentage. Whether real in-scope JNLP apps ship SWT determines if the `JNLPClassLoader`-for-SWT work is critical-path or merely defensive.
- **Timing claim (Stream 4, medium, self-flagged unverified):** "`getWindows()` from the socket thread returns empty until discovery moves to the EDT" was not reproduced on a live OWS app in-session. Experiment #3 covers it — don't build the readiness design on it until reproduced.
- **JClic player path (unresolved).** Only `reportServer.jnlp` confirmed HTTP 200; the richer player JNLP path 404'd. Re-discover before relying on it — and never gate CI on it regardless.
- **Bundled-JRE attach support (open).** Whether the OWS-bundled runtime (Adoptium JDK 11 in v1.14.0) exposes the target-side attach mechanism, or whether some trimmed JRE variants lack it. Experiment #2's JRE-only run settles this.
- **No genuine cross-stream contradiction** on the core strategy — all four streams independently land on "separate child JVM → dynamic attach is viable and preferred, `-javaagent`-in-JNLP is blocked by the whitelist." That agreement is the strongest signal in the corpus.
